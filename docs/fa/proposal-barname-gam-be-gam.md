# پروپوزال و برنامهٔ گام‌به‌گام ساخت افزونهٔ Fast Woo Sell

> هدف اعلام‌شدهٔ کاربر: **بهینه بودن و کمترین باگ ممکن**، حتی اگر ۲۰ گام طول بکشد.
> این سند سه بخش دارد: (۱) انتخاب زیرساخت، (۲) روش کار ضدباگ، (۳) ۲۰ گام با معیار پذیرش.

## بخش ۱ — زیرساخت، زبان و کتابخانه‌ها

### ۱-۱. اصل حاکم: «کمترین وابستگی»

هر کتابخانهٔ اضافه = یک منبع باگ، یک تضاد نسخه با افزونه‌های دیگر سایت، و یک وابستگی که باید سال‌ها نگه داشته شود. در اکوسیستم وردپرس، افزونه‌های کم‌باگ افزونه‌هایی هستند که **فقط از API خود وردپرس و ووکامرس** استفاده می‌کنند. بنابراین انتخاب‌ها عمداً محافظه‌کارانه‌اند.

### ۱-۲. جدول انتخاب‌ها

| لایه | انتخاب | چرا این، و نه جایگزین |
|---|---|---|
| **زبان سرور** | PHP، حداقل **7.4**، توصیه 8.1+ | اجبار وردپرس. 7.4 چون هنوز ~۲۰٪ هاست‌های ایرانی روی آن هستند؛ کد فعلی هم روی 7.4 نوشته شده. **بدون** `readonly`/`enum`/`match` |
| **پلتفرم** | WordPress ≥ 6.2، WooCommerce ≥ 8.0 | HPOS و Store API پایدار از این نسخه‌ها. همان چیزی که در `Requirements.php` هست |
| **دیتابیس** | MySQL/MariaDB از طریق `$wpdb` + `dbDelta` | هیچ ORM. ORM‌ها در وردپرس با کش آبجکت و multisite درگیر می‌شوند. **همهٔ SQL فقط در Repository‌ها** (قاعدهٔ ۲ سند ۰۴) |
| **زمان‌بندی** | **Action Scheduler** (همراه ووکامرس) | WP-Cron روی سایت کم‌ترافیک اجرا نمی‌شود و روی پرترافیک کاربر را معطل می‌کند. AS صف، retry، لاگ و UI دارد و **نصب اضافه نمی‌خواهد**. انحراف کد فعلی از این را در گام ۴ اصلاح می‌کنیم |
| **REST** | WP REST API (`register_rest_route`) | نه `admin-ajax`. قابل تست، سبک، nonce استاندارد |
| **فرانت‌اند مشتری** | **Vanilla JS (ES2017)، بدون هیچ کتابخانه** | یک فایل زیر ۶KB gzip. `tracking.js` فعلی همین‌طور است. jQuery حذف؛ React برای ویجت فروشگاه بی‌معنی است |
| **پنل ادمین** | PHP رندر سمت سرور + Settings API + Vanilla JS کم | جایگزین (React/`@wordpress/components`) برای «۴ صفحهٔ ساده» ۵۰۰KB باندل و یک زنجیرهٔ build می‌آورد که خودش منبع باگ است. `<details>` بومی برای افشای تدریجی |
| **بلوک گوتنبرگ** | فقط **یک** بلوک «server-side rendered» با `block.json` | بدون JSX؛ `render_callback` همان `Renderer` شورت‌کد را صدا می‌زند. یک منبع حقیقت برای رندر |
| **CSS** | CSS خالص با logical properties، متغیرهای رنگ پنل وردپرس | بدون Sass/PostCSS؛ نیازی به build نداریم |
| **ترجمه** | `__()` + فایل‌های `.po/.mo` + `wp i18n make-pot` | فارسی `fa_IR` از روز اول؛ اعداد فارسی با `number_format_i18n` |
| **کیفیت کد** | PHPCS + **WPCS 3.1** + PHPCompatibilityWP، **PHPStan سطح 6** با `szepeviktor/phpstan-wordpress` | PHPCS استایل و امنیت (escaping, prepare)، PHPStan **باگ‌های نوعی را قبل از اجرا** می‌گیرد — این مهم‌ترین ابزار ضدباگ در PHP است و در پروژه هنوز نیست |
| **تست واحد** | PHPUnit 9.6 + Yoast polyfills (موجود) با stubهای `tests/bootstrap.php` | منطق خالص (`Service`, `Filters`, `Cache`, ریاضی affinity) بدون وردپرس تست می‌شود؛ سریع (زیر ۲ ثانیه) |
| **تست یکپارچه** | `wp-env` (Docker) + `WP_UnitTestCase` + `WC_Helper_Product/Order` | فقط جایی که واقعاً DB و WooCommerce لازم است: Schema، Migrator، AffinityBuilder، Renderer، REST |
| **تست مرورگر** | Playwright، فقط **۳ سناریوی حیاتی** (ویجت دیده می‌شود / impression ثبت می‌شود / کلیک attribute می‌شود) | نه بیشتر؛ تست E2E زیاد = شکننده |
| **CI** | GitHub Actions: ماتریس PHP 7.4 / 8.1 / 8.3 × WP آخرین / قبلی | هر push: lint + phpstan + unit؛ هر PR: integration |
| **پکیجینگ** | `wp dist-archive` + `.distignore` | zip قابل نصب بدون `tests/`, `node_modules`, `docs/` |

### ۱-۳. چیزهایی که **عمداً استفاده نمی‌کنیم**

- ORM یا Query Builder خارجی (Eloquent, Doctrine)
- فریم‌ورک فرانت (React/Vue) برای پنل
- Composer runtime dependencies در نسخهٔ نهایی (فقط dev). دلیل: تضاد نسخه با افزونه‌های دیگر که همان کتابخانه را با نسخهٔ دیگر لود می‌کنند — یکی از رایج‌ترین fatal‌های وردپرس
- سرویس ابری، LLM، telemetry
- Tailwind/Bootstrap

## بخش ۲ — روش کار برای «کمترین باگ»

باگ در پروژه‌های افزونه از **پنج منبع** می‌آید. برای هر کدام یک سازوکار ثابت داریم:

| منبع باگ | سازوکار ما |
|---|---|
| **کدی که هرگز اجرا نشده** (وضعیت فعلی: صفر اجرا) | گام ۲: محیط `wp-env` واقعی + Seeder. **هیچ گامی «تمام» نیست تا روی فروشگاه تست دیده نشود** |
| خطای نوع/null/آرایهٔ اشتباه | PHPStan سطح 6 در CI، از گام ۳. هیچ PR با خطای PHPStan merge نمی‌شود |
| SQL و escaping | PHPCS با قوانین `WordPress.DB.PreparedSQL` و `WordPress.Security.EscapeOutput` روی **حالت خطا** نه هشدار |
| رگرسیون (تغییری که چیز دیگری را می‌شکند) | هر گام تست خودش را اضافه می‌کند، CI همهٔ تست‌های قبلی را اجرا می‌کند |
| ابهام نیاز (کد درست، ولی نه آن چیزی که می‌خواستی) | هر گام قبل از کد یک **«مینی‌طراحی» ۱۰ خطی** دارد که تو تأیید می‌کنی؛ بعد کد |

### چرخهٔ ثابت هر گام (Definition of Done)

```
۱. مینی‌طراحی (چه فایل‌هایی، چه رفتاری، چه تستی) → تأیید تو
۲. تست‌ها اول نوشته می‌شوند (حداقل: یک مسیر موفق + یک مسیر خطا)
۳. کد
۴. lint + phpstan + unit سبز (در CI، نه فقط حرف)
۵. اجرای دستی روی wp-env و ثبت اسکرین‌شات/خروجی در PR
۶. کامیت کوچک با پیام واضح؛ به‌روزرسانی tasmimat.md
۷. مرور مشترک ۱۰ دقیقه‌ای: من توضیح می‌دهم، تو سؤال می‌پرسی
```

قاعدهٔ اندازه: **هیچ گامی بیش از ~۴۰۰ خط کد جدید نیست.** اگر بزرگ‌تر شد، دو گام می‌شود.

### دربارهٔ استفاده از کد قبلی

**بله، استفاده می‌کنیم — و این تصمیم خوبی است، نه صرفاً میان‌بر.** دلایل:
- ۱۰٬۲۶۲ خط با ۰ خطای نحوی، معماری منطبق بر سند ۰۴، و تصمیم‌های سختِ درست (کسینوس، rebuild resumable، cache epoch، مرز امنیتی رویدادها).
- بازنویسی از صفر همان تصمیم‌ها را دوباره می‌گیرد و باگ‌های جدید می‌سازد.

**اما** یک شرط: چون این کد هیچ‌وقت اجرا نشده، **قبل از ساختن روی آن باید زیرش را محکم کنیم** (گام‌های ۱–۵). این «ایدهٔ بهتر» من است: نه بازنویسی، نه ادامه‌ی کورکورانه — **اول اجرا و اثبات، بعد توسعه.**
