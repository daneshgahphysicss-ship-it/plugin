# ۰۳ — اصلاحات خود کاربر روی پیشنهادهای سند ۰۱

> متن عیناً از کاربر (پاسخ به سند ۰۱، قبل از سند ۰۲). این اصلاحات همان‌هایی هستند که سند ۰۲ با عبارت «طبق اصلاح تو» به آن‌ها اشاره می‌کند. ویرایش نشده.

---

یک نکته هم درباره پیشنهاد «گرفتن شماره قبل از رها شدن»: من آن را به شکل پاپ‌آپ اجباری پیاده نمی‌کنم. این کار می‌تواند UX و conversion checkout را خراب کند. بهتر است capture شماره را در مراحل طبیعی checkout انجام دهیم و در صورت فعال‌سازی فروشنده، یک گزینه بسیار سبک برای دریافت شماره تماس جهت پیگیری سفارش ناتمام داشته باشیم.

همچنین A/B تست را از ابتدا طوری طراحی می‌کنم که فقط محدود به «عنوان ویجت» نباشد. Experiment باید بتواند این موارد را مقایسه کند:

- Engine A vs Engine B
- Widget A vs Widget B
- Rule A vs Rule B
- Position A vs Position B

و خروجی اصلی هم صرفاً CTR نباشد:

Impressions → Clicks → Add to Cart → Orders → Attributed Revenue

آزمون معناداری آماری هم فقط وقتی نمایش داده شود که sample size کافی باشد؛ نباید با ۲۰ impression نتیجه «Variant B بهتر است» بدهیم.

یک اصلاح دیگر به SQL پیشنهادی تو دارم. برای بازسازی affinity، اجرای JOIN کامل روی wc_order_product_lookup می‌تواند برای فروشگاه‌های بسیار بزرگ همچنان سنگین باشد. بنابراین من معماری را دو سطحی می‌گذارم:

- فروشگاه کوچک/متوسط: MySQL aggregation
- فروشگاه بزرگ: batched aggregation + Action Scheduler

و قبل از rebuild، تعداد سفارش‌ها و تعداد lookup rows را اندازه می‌گیریم و بر اساس آن strategy انتخاب می‌کنیم.

در مورد BINARY(16) هم من برای v1 الزامش نمی‌کنم. UUID فشرده از نظر storage جذاب است، ولی پیچیدگی تبدیل و debugging را اضافه می‌کند. اگر visitor/session واقعاً UUID باشند، CHAR(36) CHARACTER SET ascii COLLATE ascii_bin انتخاب بسیار قابل‌قبولی است. بهینه‌سازی ۶۰–۷۰٪ را هم تا benchmark واقعی انجام نشده به عنوان عدد قطعی در مستندات محصول نمی‌نویسیم.

و یک تصمیم استراتژیک دیگر: Rule Engine و Segment Engine را طوری بساز که بعداً هر سه موتور بتوانند از آنها استفاده کنند. این دو نباید داخل Recommendation دفن شوند. این کار در آینده اجازه می‌دهد مثلاً:

«مشتری VIP + سبد بالای X + محصول در حال اتمام → پیشنهاد محصول جایگزین + اولویت تماس بالا»

را بدون نوشتن منطق جدید برای هر ماژول بسازیم.

اگر قرار است همین پروژه را ادامه بدهیم، قدم بعدی من قبل از نوشتن حتی یک خط کد این است که Database Schema نهایی + Event Taxonomy + State Machine سبد رهاشده + قرارداد Recommendation Engine را دقیق کنیم. این چهار مورد ستون فقرات کل افزونه‌اند و اشتباه در آنها بعداً بازنویسی بسیار پرهزینه‌ای ایجاد می‌کند.
